装着 agent 的机器不必逐台 SSH 也能升级：hub 可以经**已经建立的那条 WebSocket** 把新版 agent 推过去，
由 agent 自己验签、替换、自检，失败就换回来。

这是**可选**的。默认关，而且只能由这台机器的主人打开——hub 读得到那个开关，改不了它。

## 前提

1. agent **≥ 1.1.10**（这个版本才认识 `--allow-remote-upgrade`）
2. 这台机器装的时候带了 `--allow-remote-upgrade`（纳管时勾**允许远程升级**，或重装时给这个参数）

<Note warn>
  先升 agent，再开这个开关。老 agent 拿到它不认识的参数会以 `unknown argument` 退出，在
  `Restart=always` 下变成反复重启。
</Note>

没开这个开关的节点，面板上不给「远程升级」按钮——它只能 SSH 重跑安装命令升级。

## 怎么升

**单台**：节点列表那一行的升级图标（开着才出现）。确认做成**两步**：先点一下，按钮就地变成
「确认」，再点一次才发出去——它会替换那台机器上的二进制，值得多问一句。

**一批**：**更新**页的**批量下发**。按顺序逐台进行，**失败即停**，不会一路刷到底。

## 过程能看到什么

下发不是黑盒，面板会依次显示：

```text
取发布物 → 推送 N%（按真实字节数）→ 等待应用 → 等待重连
```

成功的结果留 30 分钟；失败的一直留到下一次尝试，免得你回头看时找不到失败原因。

## 这边安全怎么保证

- **先验签再替换**：发布公钥**编译在 agent 二进制里**，hub 改不了；签名对不上就**不替换**，
  并把这个事实回报给面板
- **字节同源**：hub 推给节点的二进制与 `/agent/{arch}` 转发给新装节点的是同一个来源，
  所以「hub 能装节点」与「hub 能升级节点」见到的是同一份字节
- **换下来的留一份**：替换前把当前的二进制留成 `.prev`
- **换上去要自证**：新版本启动后要能跑起来、并连上 hub；撑不过这段自检就**自动换回 `.prev`**
- **崩了就停**：服务单元设了启动上限（5 分钟内崩 5 次就停止重启），一个「启动即崩」的坏版本不会
  无限重启把 CPU 和日志打满——它会停在那儿等你，`systemctl status` 看得见
- **版本只升不降**：agent 拒绝不比当前新的公告，也不接受非加密连接上的升级

## 升完之后

面板的**版本**列会显示新版本；「更新」页的待升级列表里这台就消失了。

## 出问题时

**按钮是灰的** → 这台没开 `--allow-remote-upgrade`，或者 agent 太旧（< 1.1.10）。

**一直停在「等待重连」** → 新版起来了但没连上 hub。看那台机器的日志：

```bash
journalctl -u monitor-agent -n 50
```

**升级后版本没变** → 多半是验签没过或自检没过，已经自动回滚。面板上的失败原因会写明是哪一种。

**想回到旧版** → 远程升级不带降级。把旧二进制留在 `.prev` 上的那台，可以手动换回去；更稳妥的做法是
用安装命令重装。
